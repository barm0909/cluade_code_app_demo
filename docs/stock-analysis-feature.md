# 在庫分析機能（ABC分析・在庫回転率・滞留在庫・発注点提案）

入出庫帳票（ledger）に積み上がった**出庫実績**と現在庫を突き合わせて、
「どの商品が稼いでいるか（ABC）」「在庫を何日分抱えているか（回転）」
「動いていない在庫はどれか（滞留）」を出す **在庫分析タブ** を追加した機能です。

これまで在庫の"多い/少ない"は `Product.minQuantity`（発注点）という**手入力の固定値**との
比較でしか判断できず、実際にどれだけ出ているかは帳票を目で追うしかありませんでした。
そのため「ほとんど動かないのに在庫を持ち続けている商品」「出荷ペースに対して発注点が
低すぎる／高すぎる商品」を見つける手段がありませんでした。

専用の永続データ（新しいテーブル）は増やしていません。ロット追跡・廃棄ロス集計・原価履歴と同じく
**商品マスタ × 帳票から組み立てる**方式で、**マイグレーションはありません**。

唯一の例外が発注点の見直し提案で、これだけは `Product.minQuantity` を書き換えます
（在庫は動かないので帳票には何も書きません）。

---

## データモデル

新しい永続データはありません。集計に使うのは既存の値だけです。

| 使うもの | 何に使うか |
|----------|-----------|
| `StockTransaction.type` / `quantity` / `date` / `productId` | 期間内の出庫数、最終出庫日 |
| `Product.costPrice` | 出庫金額（＝ ABC のランク付けの基準） |
| `Lot.quantity` / `lotUnitCost(lot, product)` | 現在庫数・現在庫金額 |
| `Supplier.leadTimeDays` | 発注点の提案値（リードタイム分） |
| `InboundPlan.supplierId` / `createdAt` | どの仕入先のリードタイムを使うかの判定 |

### 集計の前提（概算になっている箇所）

- **出庫金額は `出庫数 × 商品の現在の原価`** です。帳票に単価が残っているのは「入荷」と「廃棄」だけなので、
  出庫時点の原価は再現できません（廃棄ロス金額のフォールバックと同じ割り切り）。
  ABC はランク付けが目的なので、順位が決まればよいという判断です。
- **在庫回転率は `期間出庫数 ÷ 現在庫数`** です。期間中の平均在庫は持っていない（在庫の
  スナップショット履歴がない）ため、現在庫で代用しています。
- **在庫日数は `現在庫数 ÷ 1日あたり出庫数`**。出庫実績が0なら「減らない」ので `null`（画面では `—`）。

---

## 集計のルール

### 出庫の数え方

- 出庫 = `売上出庫` + `調整出庫` + `廃棄`（`OUTBOUND_TYPES`）。
  **移動は総在庫を動かさないので数えません**。入庫系も数えません。
- 内訳として `salesQuantity`（売上出庫）と `disposalQuantity`（廃棄）を別に持ちます。
- 集計期間は 30 / 90 / 180 / 365日から選択（既定 90日）。「今日を含む直近N日」なので、
  90日なら開始日は89日前（`analysisPeriodStart`）。

### 最終出庫日だけは期間で絞らない

滞留の判定は「いつから動いていないか」なので、期間の外の記録も見ます。
期間で切ってしまうと「200日前に出たきりの商品」と「一度も出ていない商品」が区別できなくなるためです。

| `lastOutboundAt` | `stagnantDays` | 意味 |
|------------------|----------------|------|
| 記録あり | 経過日数 | その日から動いていない |
| 空文字 | `null` | 出庫実績が一度もない |

### ABCランク

出庫金額の大きい順に並べ、累計構成比で切ります。

| ランク | 条件 |
|--------|------|
| A | 累計構成比が 70%（`ABC_A_SHARE`）に達するまで |
| B | 90%（`ABC_B_SHARE`）に達するまで |
| C | それ以降、および**出庫金額が0の商品** |

境目をまたぐ商品は**上のランクに含めます**（ABC分析の慣習）。判定は「その商品を足す**前**の累計」で
行うため、1商品で95%を占めるようなケースでもその商品自身は A になります。
出庫が1件もない場合は全商品が C（構成比0）です。

### 滞留在庫

`isStagnant(row, thresholdDays)` が真の商品。しきい値は 30 / 60 / 90日から選択（既定60日）。

- 在庫が残っていない商品は**滞留に数えません**（滞留しているのは「在庫」なので）。
- 出庫実績が一度もない商品（`stagnantDays === null`）は在庫があれば滞留扱いです。

### 発注点の見直し提案

```
提案値 = ceil(1日あたり出庫数 × (標準リードタイム + 安全在庫日数))   ※最低1
```

- 安全在庫日数は 3 / 7 / 14日から選択（既定7日）。
- 標準リードタイムは**直近に作った（キャンセルでない）入荷予定の仕入先**から引き継ぎます。
  取引停止・削除済みの仕入先は引き継がず 0日扱い — `reorderSuggestions`（発注提案）と同じルールです。
- **期間内に出庫のなかった商品は提案しません。** 出庫ペース0から機械的に計算すると発注点が
  下がってしまい、たまにしか動かない商品が欠品するためです（そうした商品は滞留在庫として別に見ます）。
- 現在値と同じになる商品も提案に出しません。
- 並びは「ずれの大きい順」＝直す価値の大きい順。

## 画面（`StockAnalysisView.tsx`）

タブ順は**最後**（`在庫分析`）。ダッシュボードと同じく
自前のサマリカードを持つため、App.tsx 側で共通のアラートバナー・サマリ行を非表示にしています。

```
[在庫金額][期間の出庫金額][在庫日数][Aランク商品][滞留在庫]   ← サマリカード

■ ABC分析（出庫金額の構成比）        集計期間[直近90日▼]
  [検索][カテゴリ▼][ランク▼]  [CSVエクスポート（在庫分析）]
  ランク/商品名/SKU/カテゴリ/在庫数/在庫金額/期間出庫数/出庫金額/構成比/回転率/在庫日数/最終出庫

■ 滞留在庫（在庫はあるのに動いていない商品）   判定[60日以上▼]
  商品名/SKU/在庫数/在庫金額/最終出庫/滞留日数

■ 発注点の見直し提案                 安全在庫[7日分▼]
  [✓]/商品名/SKU/1日あたり出庫/リードタイム/現在の発注点/提案値/差
  → [すべて選択] [選択したN件を反映]  （確認ダイアログののち一括更新）
```

画面が持つ状態は「集計期間・滞留しきい値・安全在庫日数・絞り込み・選択中の商品」だけで、
集計はすべて `useInventory.ts` の純粋関数に任せています（`DashboardView` と同じ構成）。

## 実装

| 関数 | 役割 |
|------|------|
| `analysisPeriodStart(days, today?)` | 「今日を含む直近N日」の開始日（ローカル日付 `YYYY-MM-DD`） |
| `stockAnalysisRows(products, ledger, options?)` | 商品別の集計本体。出庫金額の大きい順に並べ、ABCランクまで振る |
| `isStagnant(row, thresholdDays?)` / `stagnantRows(rows, thresholdDays?)` | 滞留の判定と一覧（金額の大きい順） |
| `stockAnalysisTotals(rows, options?)` | サマリカード（在庫金額・出庫金額・在庫日数・ランク別件数・滞留） |
| `filterStockAnalysis(rows, filter)` | キーワード／カテゴリ／ランクで絞り込み |
| `minQuantitySuggestions(rows, products, inboundPlans, suppliers, options?)` | 発注点の提案（プレビュー用の純粋関数） |
| `planMinQuantities(suggestions, productIds)` | 選択された提案 → 更新入力。確認ダイアログと実行が同じ結果を共有する（`planReorder` / `planDisposal` と同じ作り） |
| `stockAnalysisCsv(rows, categories)` / `exportStockAnalysisCsv` | CSV（`CSV_EXPORTS.analysis`、`在庫分析_YYYY-MM-DD.csv`） |
| `applyMinQuantities(updates)`（フック） | 発注点の一括更新。1回の state 更新・1回の PUT。帳票には書かない |

`applyMinQuantities` は「実際に値が変わる商品の数」を返します。存在しない商品・現在値と同じ値・
負の値は無視されます（更新件数にも含めません）。

### 他機能との関係

- 更新した発注点はそのまま**ダッシュボードの要発注・発注提案の基準**になります
  （`lowStockRows` / `reorderSuggestions` が `minQuantity` を見ているため）。
  在庫分析で発注点を直す → ダッシュボードで発注する、という流れになります。
- 商品マスタの発注点欄を手で直すのと同じ値を書き換えているだけなので、片方だけが正しい、
  ということは起きません。

テストは純粋関数が `src/test/stockAnalysis.test.ts`、画面が `src/test/StockAnalysisView.test.tsx`、
フックの `applyMinQuantities` が `src/test/useInventory.test.ts` です。
