# ロットトレーサビリティ（ロット追跡）機能

食品でリコールが起きたときに必要になるのは「**このロットが、いつ入って、どこを経由して、いつ出たか**」です。
従来はその情報を入出庫帳票からロットNoでキーワード検索し、目視で追う必要がありました。
ロット追跡タブは、ロットを1つ選ぶだけで同じことを時系列のカードで見せます。

必要な記録はすべて帳票（`ledger`）に残っているため、**専用の永続データは持ちません**。
DBマイグレーションも Worker API の追加も不要で、既存データに対してもそのまま機能します。

---

## 画面

タブ構成の最後（入出庫帳票の右）に「ロット追跡」タブが追加されます。
在庫一覧タブの**ロット行**にも「追跡」ボタンが増え、押すとそのロットを選択した状態でこのタブへ移動します。

### ロットの選択

```
[ロットNo・商品名・SKUで検索...]

6件   追跡したいロットの「追跡」を押すと、入荷から出庫までの履歴を時系列で表示します。

 商品名  SKU     ロットNo  賞味期限  現在庫  記録件数  最終記録           操作
 牛乳    ML-001  20260818  3日後         4         3  2026/08/15 12:55   [追跡]
 チーズ  CS-001  20260813  期限切れ      2         0  —                  [追跡]
```

- 候補には**在庫の残っているロット**に加えて、**帳票にしか残っていないロット**（出しきった・廃棄した・
  ロットごと削除した）も並びます。リコールの連絡は在庫を出しきった後に来るため、
  現在庫だけを候補にすると肝心のロットが追跡できないからです。
- 並びは「最後に動いた日時の新しい順」→商品名→ロットNo。記録のないロット（初期在庫など）は最後に来ます。
- 検索欄はロットNo・商品名・SKUの部分一致です。

### 追跡結果

サマリカード（入庫合計 / 出庫合計 / 帳票上の残数 / 現在庫 / 記録件数）＋現在の在庫＋履歴カードの3段構成です。

```
[← ロットの選択に戻る]  牛乳 ML-001  ロット 20260818     [CSVエクスポート（ロット追跡）]

 入庫合計 +24    出庫合計（既に出た数量） -6    帳票上の残数 18    現在庫 18    記録件数 4
 入荷 24         売上出庫 4 / 廃棄 2            入庫 − 出庫       販売倉庫     移動 1件

 現在の在庫   経路: 販売倉庫 → 保留倉庫
 倉庫        賞味期限  在庫数
 🟢販売倉庫   3日後        18

 履歴（古い順）  2026/08/10 09:00 〜 2026/08/15 12:55
 ● 入荷      2026/08/10 09:00  +24            残 24
   🟢販売倉庫   入荷予定（山田乳業）
 ● 移動      2026/08/12 14:20   5             残 24
   🟢販売倉庫 → 🟠保留倉庫   倉庫移動
 ● 売上出庫  2026/08/15 12:55  -4             残 20
   🟠保留倉庫   FEFO出庫
```

- 履歴は**古い順**（入荷 → 移動 → 出庫）に並びます。帳票タブが新しい順なのと逆なのは、
  「入ってから出るまで」を上から順に読むためです。
- 各カードの右端の「残 N」は、その記録の**直後**のロット残数（入庫の累計 − 出庫の累計）です。
  移動では増減しません（倉庫が変わるだけで総数は変わらないため）。
- 「経路」は帳票に出てくる倉庫を初めて現れた順に並べたものです。

### 数字が合わないとき

「帳票上の残数」と「現在庫」は原則一致しますが、次の場合はずれます。画面上でも注意書きを出します。

| 状態 | 表示 |
|------|------|
| 記録が1件もない（帳票を記録する前からある在庫。サンプルデータ・リセット直後） | 「入出庫の記録がありません。」の案内 |
| 記録はあるが残数と現在庫が違う（記録前からの在庫が混ざっている） | 「帳票上の残数と現在庫が一致しません。」の警告 |

帳票を記録し始める前の在庫にはさかのぼって記録を作らない方針なので、この差は**エラーではありません**。

## ロットNoは商品とセットで扱う

ロットNoは賞味期限から自動生成する（`generateLotNo`）ため、**期限が同じなら別商品でも同じ番号**になります。
`20260701` だけで帳票を検索すると牛乳とチーズが混ざる、というのが従来の目視追跡の弱点でした。

そのため追跡の対象は必ず「商品 + ロットNo」の組（`LotTraceKey`）で指定します。
候補一覧も、同じロットNoでも商品が違えば別行になります。

一方、同じ商品の中では**同じロットNoが複数の倉庫に分かれている**ことがあります
（部分移動は移動先に「同じロットNo・別id」のロットを作るため）。これは同一のロットなので
1つの追跡対象としてまとめ、現在の在庫だけを倉庫ごとに分けて表示します。

---

## 時系列の復元

帳票は新しい記録を先頭に積みます（`addTransactions` が prepend する）が、
1回の操作でまとめて記録した分（FEFO出庫の引当ごとの記録、ロット編集の 移動＋数量調整 など）は
**日時が同一のまま「記録した順」**で並んでいます。単純に配列を逆順にすると、この塊の中だけ順序が狂います。

`chronologicalLedger` は「同じ日時が続く塊」を保ったまま塊の並びだけを逆にし、
最後に日時で安定ソートすることで本来の時系列に戻します。
（D1 から読み直したときの `ORDER BY date DESC` でも同じ前提が成り立ちます。）

## 実装

集計は `src/useInventory.ts` の純粋関数、`src/LotTraceView.tsx` は表示と選択状態のみを担当します
（`LedgerView` / `StocktakeView` / `DashboardView` と同じ構成）。

| 関数 | 役割 |
|------|------|
| `traceLot(ledger, lotNo, options?)` | 1ロットの履歴（`events` / `inbound` / `outbound` / `balance` / 区分別内訳 / 経由倉庫）を組み立てる。`options.productId` で商品を限定 |
| `chronologicalLedger(txns)` | 帳票を古い順に並べ直す |
| `lotTraceCandidates(products, ledger, keyword?)` | 追跡できるロットの候補一覧（在庫にあるロット＋帳票にしかないロット） |
| `lotStockRows(products, key)` / `lotStockQuantity(products, key)` | いまどの倉庫にいくつ残っているか（在庫0のロットは除く） |
| `lotTraceCsv(trace, warehouses)` / `exportLotTraceCsv(...)` | 追跡結果のCSV（`CSV_EXPORTS.trace`、`ロット追跡_YYYY-MM-DD.csv`） |
| `isSameLotTraceKey(a, b)` | 追跡対象の同一判定 |

追跡中のロット（`LotTraceKey | null`）は `App.tsx` が持ちます。在庫一覧の「追跡」ボタンが
タブ切り替えと同時にこの状態を設定するためで、`LotTraceView` 自身は `target` / `onTargetChange` を
受け取るだけです（検索キーワードだけがビューのローカル状態）。

**この機能は状態を一切変更しません**（読み取り専用）。帳票に記録を追加することもないので、
`data-and-rules.md` の操作→帳票の対応表に追加する行はありません。

テストは純粋関数が `src/test/lotTrace.test.ts`、ビューが `src/test/LotTraceView.test.tsx` です。
