## Commands

```bash
npm run dev            # start Vite dev server (proxies /api → localhost:8787)
npm run dev:api         # wrangler dev — Worker API + local D1 (run alongside npm run dev)
npm run build            # tsc -b (typecheck incl. worker) then vite build
npm run lint              # oxlint
npm run test               # vitest run (single run, CI mode)
npm run test:watch          # vitest watch mode
npm run test:coverage        # vitest run --coverage (v8 provider)

npm run db:migrate           # apply migrations/ to the LOCAL D1 (.wrangler/state)
npm run db:migrate:remote     # apply migrations to the REMOTE D1 (needs wrangler login)
npm run db:seed                # load seed.sql into the local D1 (re-runnable)
npm run db:query -- "SQL"       # run arbitrary SQL against the local D1
```

Run a single test file: `npx vitest run src/test/warehouse.test.ts`
Run a single test by name: `npx vitest run -t "test name substring"`

There is no separate typecheck script — `npm run build` runs `tsc -b` as its first step, so a failing build often means a type error rather than a bundling error.

Note that `npm run test` and `npm run lint` do not type-check (Vitest transforms TS without full type-checking and oxlint's `typeAware` option is off), so don't assume the build is green just because tests/lint pass — run `npm run build` (or `tsc -b` directly) to verify types.

## Architecture

React 19 + TypeScript + Vite SPA with a thin Cloudflare Worker backend (`worker/index.ts`) that persists all state to **D1** (SQLite). The same `DB` binding resolves to a local SQLite file under `.wrangler/state/` during `wrangler dev` and to the remote Cloudflare D1 database once deployed — the Worker code is identical in both.

- `wrangler.jsonc` is the single config for both local dev and deploy (`main` worker + `assets` + `d1_databases`). The `database_id` is a placeholder until someone runs `npx wrangler d1 create inventory-db` and pastes the real id — `wrangler deploy` fails until then. Changing `database_id` also re-keys the local D1 state, so re-run `npm run db:migrate && npm run db:seed` after touching it.
- Local dev needs two processes: `npm run dev` (Vite, HMR) and `npm run dev:api` (Worker + local D1 on :8787); Vite proxies `/api` to the latter. `wrangler dev` requires `dist/` to exist (run `npm run build` once).
- DB schema lives in `migrations/` (`0001_init.sql`: `products`, `lots`, `warehouses`, `stock_transactions`; `0002_categories.sql`: `categories` + `products.category_id`; `0003_product_jan_code.sql`; `0004_inbound_plans.sql`: `inbound_plans`; `0005_suppliers.sql`: `suppliers` + `inbound_plans.supplier_id`; `0006_cost_history.sql`: `inbound_plans.unit_price` + `stock_transactions.unit_price`/`supplier_id`; `0007_lot_unit_price.sql`: `lots.unit_price`; `0008_inbound_plan_printed.sql`: `inbound_plans.printed_at`; `0009_purchase_order_prints.sql`: `purchase_order_prints`; `0010_sales.sql`: `customers` + `stock_transactions.customer_id`/`cost_unit_price`; `0011_tax_rate.sql`: `products.tax_rate` + `stock_transactions.tax_rate`; `0012_product_kind.sql`: `products.kind` + a rebuild of `stock_transactions` to widen its `type` CHECK for `資材使用` (SQLite can't ALTER a CHECK — any future new transaction type needs the same rebuild); `0013_sales_orders.sql`: `sales_orders`; `0014_sales_documents.sql`: `sales_document_items`; `0015_returns.sql`: another `stock_transactions` rebuild adding `売上返品`/`仕入返品` to the `type` CHECK plus `return_of_txn_id`; `0016_payments.sql`: `payment_items`; `0017_billing_closing.sql`: `customers.closing_day`/`payment_months`/`payment_day` + `sales_document_items` 繰越 columns — a normalized form of the `useInventory.ts` model, snake_case columns). `seed.sql` mirrors `SAMPLE_DATA` / `SAMPLE_INBOUND_PLANS` / `DEFAULT_CATEGORIES` / `DEFAULT_SUPPLIERS` / `DEFAULT_CUSTOMERS` / `SAMPLE_SALES_ORDERS` (plus a few sample 売上出庫 rows). Keep all three in sync when the data model changes, and keep the worker's local type copies in `worker/index.ts` in sync too (it can't import `useInventory.ts` because that would pull react/xlsx into the Worker bundle).

### State lives in one hook: `useInventory.ts`

Everything — types, sample data, persistence, and all mutations — is defined in `src/useInventory.ts`, not spread across a `types.ts`/store/reducer split. `App.tsx` and the modal components import their types (`Product`, `Lot`, `Warehouse`, `StockTransaction`, `SortField`, etc.) directly from `./useInventory`.

- `src/types.ts` is a **stale leftover** from an earlier version of the data model (it lacks `lots`, `costPrice`, warehouses) and is not imported anywhere. Don't add new types there — extend `useInventory.ts` instead, or delete `types.ts` if you're cleaning up.

Persistence is slice-based via the Worker API: `GET /api/state` returns everything on mount; each mutation fire-and-forgets a full-replace `PUT /api/products` / `/api/warehouses` / `/api/categories` / `/api/ledger` / `/api/inbound-plans` / `/api/suppliers` / `/api/customers` / `/api/purchase-order-prints` / `/api/sales-orders` / `/api/sales-documents` / `/api/payments` (see `persist()` in `useInventory.ts`). There is no localStorage anymore. When the API is unreachable (offline, jsdom tests), the hook runs purely in memory, starting from `SAMPLE_DATA` / `DEFAULT_WAREHOUSES` / `DEFAULT_CATEGORIES` / `DEFAULT_SUPPLIERS` / `DEFAULT_CUSTOMERS` / `SAMPLE_SALES_ORDERS` — that fallback is what most tests rely on; tests that verify persistence stub `fetch` with `src/test/mockApi.ts`. A fresh (empty) remote DB shows an empty inventory until リセット (`resetToSample()`) is clicked, which PUTs the sample data; the local DB is instead populated by `npm run db:seed`.

### Data model

- `Product` has many `Lot`s (lot-level tracking by expiry date, warehouse, and cost), not a single quantity field. `totalQuantity(product)` and `totalQuantityByWarehouse(product, warehouseId)` sum across lots. `Lot.unitPrice?` is the lot's actual cost; `lotUnitCost(lot, product)` (`= lot.unitPrice ?? product.costPrice`) is the one helper every valuation calc (`dashboardTotals`, `expiringLotRows`, `warehouseSummaries`, `categorySummaries`, `planDisposal`, `stocktakeRows`) goes through — never read `product.costPrice` directly when a specific lot is in scope. `lowStockRows` is the one exception (forecasting stock not yet on hand, so it has no lot to reference).
- Every `Lot` has a `warehouseId`. Loading old data without `warehouseId` migrates it to `DEFAULT_WAREHOUSE_ID` (`wh-sales`) — preserve this backward-compat mapping in `migrateProducts()` if you touch it.
- `Product.categoryId` references the `categories` master (`Category { id, name }`, managed via `addCategory`/`updateCategory`/`deleteCategory`; delete is blocked while any product uses the category). Renaming a category propagates everywhere because products hold the id, not the name. Loading old data with a legacy `category` string maps it to an existing category by name (or creates one, falling back to `未分類`) in `migrateProducts()`.
- Any quantity-changing operation (`addLot`, `adjustLotQuantity`, `moveLot`, `shipFefo`, `recordSale`, `returnSale`, `returnToSupplier`, `disposeLots`, `receiveInboundPlan`, `importExcel`, `applyStocktake`) also appends to the `ledger` via `addTransaction` (or `addTransactions` for batches like 棚卸, which records all rows in one state update / one PUT), recording it as `入庫`/`出庫`/`移動`. If you add a new mutation that changes stock, wire it into the ledger the same way so 入出庫帳票 stays accurate. `applyMinQuantities` (在庫分析's 発注点 bulk update) is the one batch mutator that deliberately writes **no** ledger row — it only changes `Product.minQuantity`, and no stock moves.
- `shipFefo(productId, quantity, options?)` is the product-level出庫: it ships from the earliest-expiring lots first (FEFO). The allocation itself is the pure `planFefoShipment(product, quantity, options)`, which `ShipFefoModal` also uses for its live preview — keep the two sharing that function so the preview can't diverge from what actually ships. Expired lots are excluded unless `includeExpired` is set, and one ledger row is written per allocated lot. See `docs/fefo-feature.md`.
- `Supplier` (仕入先マスタ) is referenced by `InboundPlan.supplierId`, never by name, so renaming a supplier propagates everywhere (same rule as categories/warehouses). Loading old data whose plans carry the legacy free-text `supplier` maps it to a supplier by name (creating one if needed) in `migrateInboundPlans()`. A supplier referenced by any plan **cannot be deleted** — set `active: false` (取引停止) instead, which hides it from the plan form's options (`selectableSuppliers` keeps the currently selected one). Validation lives in the pure `supplierValidationError`, shared by `SupplierModal` and `addSupplier`/`updateSupplier`. See `docs/supplier-feature.md`.
- `Customer` (得意先マスタ) is the sales-side twin of `Supplier`: it is referenced **by id** from the `売上出庫` rows of the ledger (`StockTransaction.customerId`), so renaming a customer propagates everywhere, and a customer with any sale recorded **cannot be deleted** — set `active: false` (取引停止) instead, which hides it from the sale forms (`selectableCustomers`). Validation lives in the pure `customerValidationError`, shared by `CustomerModal` and `addCustomer`/`updateCustomer`.
- **売上管理 derives everything from the ledger** — there is no sales table. A `売上出庫` row (and the `売上返品` that copies it) may carry `unitPrice` (実売単価), `customerId` and `costUnitPrice` (the lot's cost at ship time, from `lotUnitCost`), written by the shared `saleFields()` helper from `shipFefo`/`recordSale` and from `adjustLotQuantity` (lot-row 出庫). `costUnitPrice` exists because the sold lot shrinks away, so the cost behind 粗利 can't be looked up later — same reason `disposeLots` stamps `unitPrice` on 廃棄 rows. A sale price of `0` means 未入力 (not "free"), exactly like `InboundPlan.unitPrice`: it isn't written to the ledger, and `salesRows` falls back to `Product.price` / `Product.costPrice` with `estimatedPrice`/`estimatedCost` flags (a documented approximation, like 廃棄ロス on old records). `FefoAllocation.unitCost` / `FefoPlan.cost` carry the same costs into the modals' 粗利 preview so the preview can't diverge from what gets recorded. 在庫分析's 出庫金額 stays cost-based (`出庫数 × Product.costPrice`) on purpose — revenue lives in 売上管理. See `docs/sales-feature.md`.
- **消費税: every price is tax-exclusive (税抜)** — `Product.price`/`costPrice`, `Lot.unitPrice`, every `StockTransaction.unitPrice`. Tax is never stored as an amount, only as a rate: `Product.taxRate?: TaxRate` (`8` 軽減 / `10` 標準, per product; missing = `DEFAULT_TAX_RATE` 8 via `productTaxRate`, and `migrateProducts` fills it in). `saleFields()` snapshots the product's rate onto each `売上出庫` row as `StockTransaction.taxRate` (same reason as `costUnitPrice`: later rate changes must not rewrite past sales). Tax is rounded **per ledger row** with `taxAmount` (`Math.round`), and since one sale becomes one row per allocated lot, the modals' previews use `saleAmounts(allocationQuantities, unitPrice, rate)` so the preview can't diverge from `salesRows`. Old sale rows without `taxRate` fall back to the product's current rate **without** an estimated flag (flagging would mark every pre-tax-feature sale as 概算). 粗利/粗利率/構成比 and 在庫分析's 出庫金額 stay tax-exclusive. New products default their rate to the category's most common one (`defaultTaxRateForCategory`).
- **商品区分**: `Product.kind?: ProductKind` (`販売品` / `資材`; missing = 販売品 via `productKind`/`isMaterial`, filled in by `migrateProducts`). A 資材 (e.g. 値札ラベル) is stock you track but never sell: it is excluded from `SalesEntryModal`'s choices and `recordSale` refuses it (no stock move, whole quantity returned as shortage), its 販売定価/税率 inputs are hidden (values kept, not cleared — so 在庫総額 still counts a stored price), and its outbound type is the dedicated `資材使用`. The per-product outbound choices come from `outboundTypesFor(product)` (販売品: 売上出庫/調整出庫/廃棄, 資材: 資材使用/調整出庫/廃棄) — `ShipFefoModal` and `StockIoModal` use it, and `shipFefo`/`adjustLotQuantity` record a disallowed type (資材の売上出庫, 販売品の資材使用) as `調整出庫`. 在庫分析 ranks ABC over 販売品 only (`StockAnalysisRow.rank` is `null` for 資材, and 資材 are excluded from the share denominator) but still counts `資材使用` as outbound, so stagnation/発注点 suggestions cover 資材. Tested in `src/test/productKind.test.ts`.
- **返品** (`docs/return-feature.md`): two ledger types, `売上返品` (direction `in`) and `仕入返品` (`out`), with `StockTransaction.returnOfTxnId` pointing at the original `売上出庫` (required) / `入荷` (when found). They are **not** in `INBOUND_TYPES`/`OUTBOUND_TYPES`/`outboundTypesFor` — those are the hand-pickable choices of the 入庫/出庫 forms — so `transactionDirection` special-cases them and `ALL_TRANSACTION_TYPES` lists them separately (`RETURN_TYPES`). `returnSale` (from 売上管理's 明細 → `SalesReturnModal`) puts stock back into the sale's `lotNo` (merging into a lot with the same lotNo + warehouse + expiry, else recreating it; expiry recovered from a sibling lot or the YYYYMMDD lotNo) and copies the sale's `unitPrice`/`customerId`/`costUnitPrice`/`taxRate`; it is capped at sold − already returned (`returnableSaleQuantity`). `salesRows` turns `売上返品` into **negative** rows (`isReturn`), so every sales total/summary nets returns by plain summation; `taxAmount` rounds sign-symmetrically so a return's tax mirrors its sale's. `salesDocumentLines` keeps returns as separate negative lines and only 請求書 includes them (`includeReturns`). `returnToSupplier` (lot row → `PurchaseReturnModal`) shrinks the lot (left at 0 like other 出庫) and records supplier + 返品単価. 在庫分析 subtracts 売上返品 from outbound (floored at 0) and ignores 仕入返品 entirely (not demand). Previews share `planSalesReturn`/`planPurchaseReturn` with the mutators. Returns don't roll back `SalesOrder.shippedQuantity` / `InboundPlan.receivedQuantity`. Tested in `src/test/returns.test.ts`.
- `InboundPlan.unitPrice` (仕入単価, optional at entry, 0 = not set) is copied onto the `StockTransaction` that `receiveInboundPlan` writes (`unitPrice`/`supplierId`, both optional). `costHistoryRows(ledger, suppliers)` reads them back out to build the read-only 原価履歴 tab, the same "derive from the ledger" pattern as disposal loss and lot trace. It does **not** write back to `Product.costPrice`. `StockTransaction.unitPrice` is also written on each `廃棄` row `disposeLots` creates (see 一括廃棄 below) and on 売上出庫 rows that recorded a sale price (see 売上管理 above) — 入荷, 廃棄, 売上出庫 and the two return types (売上返品 copies the sale price, 仕入返品 holds the 返品単価) are the only transaction types that carry it. See `docs/cost-history-feature.md`.
- `receiveInboundPlan` also sets the *lot's* `unitPrice` (not just the ledger row's): a brand-new lot gets `plan.unitPrice` outright; merging into an existing lot (same lotNo + warehouse + expiry) blends the two with `mergedLotUnitPrice`, a quantity-weighted average of the existing lot's `lotUnitCost` and the newly-received price (rounded to the nearest yen). An input `unitPrice` of `0` (未入力) never overwrites a lot's existing cost — it's treated as "unknown", not "free". `moveLot`'s partial-split branch copies the source lot's `unitPrice` onto the new lot unchanged (a warehouse move isn't a repurchase).
- `InboundPlan` (入荷予定) is one of the two entities that are *not* stock (the other is `SalesOrder`, below): it holds what has been ordered but not yet arrived, and turns into a `Lot` only through `receiveInboundPlan`. Its status (`未入荷`/`一部入荷`/`入荷済`/`キャンセル`) is **derived** by `inboundPlanStatus` from `receivedQuantity`/`quantity`/`canceledAt` — don't add a stored status field. The allocation is the pure `planReceipt(plan, product, input)`, shared by `ReceiveInboundModal`'s preview and the mutator, which clamps to the remaining quantity (no over-receipt) and merges into an existing lot when lotNo + warehouse + expiry all match. `deleteProduct` also drops that product's plans, and `deleteWarehouse` is blocked while a pending plan targets the warehouse. See `docs/inbound-feature.md`.
- `moveLot` full-quantity moves just update the lot's `warehouseId` in place; partial moves shrink the source lot and create a new lot (new id, same `lotNo`) in the target warehouse, then record both an outgoing and incoming ledger transaction.

### Component structure

- `App.tsx` — single top-level component holding all UI state (filters, sort, modals, active tab) and rendering the product/lot table plus the ledger tab. Product rows expand inline to show a nested lot table.
- `ProductModal.tsx` / `LotModal.tsx` — controlled create/edit forms for products and lots, taking `onSave`/`onClose` props; App.tsx decides whether `onSave` calls the `add*` or `update*` mutator based on whether it's editing `null`/`'new'` vs an existing record.
- `MoveLotModal` / `StockIoModal` — defined inline inside `App.tsx` (not separate files) since they're tightly coupled to the lot table's row actions.
- `ShipFefoModal.tsx` — the FEFO出庫 form opened from a product row (not a lot row). It renders a live allocation preview from `planFefoShipment` and blocks submission while `shortage > 0`; `App.tsx` reports the executed plan through `notify`.
- `InboundPlanView.tsx` — 入荷予定 tab (between 在庫一覧 and 商品マスタ). Owns the filter state (keyword / expected-date range / status / warehouse) and the two modals it opens: `InboundPlanModal.tsx` (create/edit) and `ReceiveInboundModal.tsx` (receive). Like the other views, filtering/aggregation/CSV are pure functions in `useInventory.ts` (`inboundPlanRows`, `inboundPlanTotals`, `inboundPlanCsv`, `exportInboundPlanCsv`) tested in `src/test/inboundPlan.test.ts`.
- `SalesOrder` (受注 / 出荷予定) is the sales-side twin of `InboundPlan`: what a customer ordered but hasn't been shipped yet. Status (`未出荷`/`一部出荷`/`出荷済`/`キャンセル`) is **derived** by `salesOrderStatus` from `shippedQuantity`/`quantity`/`canceledAt`. 引当 is **never stored** — `salesOrderAllocations(orders, products)` recomputes it every render by running `planFefoShipment` over a working copy of the lots for each order with 受注残, in 出荷予定日 → createdAt order, so earlier orders consume stock first and any other stock change (売上登録, 廃棄, 棚卸 …) is reflected automatically; `salesOrderRows` computes it over **all** orders before filtering. Shipping (`shipSalesOrder`) goes through the pure `planSalesOrderShipment` (clamps to 受注残, uses the order's warehouse; shared with `ShipSalesOrderModal`'s preview) and then `shipFefo` with type `売上出庫` + the order's `unitPrice`/`customerId`, so it writes ordinary 売上出庫 rows (note `受注出荷（得意先名）`) and 売上管理 needs no changes; it may take stock that the 引当 estimate earmarked for another order. Validation is the shared `salesOrderValidationError` (資材 can't be ordered, customer required). `deleteProduct` drops the product's orders, `deleteWarehouse` is blocked while a pending order ships from the warehouse, and `deleteCustomer` is blocked while **any** order (even canceled/shipped) references the customer. Tested in `src/test/salesOrder.test.ts` / `src/test/SalesOrderView.test.tsx`. See `docs/sales-order-feature.md`.
- `SalesOrderView.tsx` — 受注 tab (between 入荷予定 and 売上管理). Mirrors `InboundPlanView` (keyword / 出荷予定日 range / status / customer filter, CSV, add/edit/cancel/delete/ship row actions) and owns `SalesOrderModal.tsx` (create/edit) and `ShipSalesOrderModal.tsx` (ship, with FEFO preview + `saleAmounts`).
- `SalesView.tsx` — 売上管理 tab (between 受注 and 商品マスタ). Owns its filter, the 明細/商品別/得意先別/日別 switch and the entry modal; everything else is pure functions in `useInventory.ts` (`salesRows`, `filterSales`, `salesTotals`, `salesProductSummaries`/`salesCustomerSummaries`/`salesDailySummaries`, `salesCsv`, `salesSummaryCsv`) tested in `src/test/sales.test.ts`. Its one mutation is 売上登録 → `SalesEntryModal.tsx` → `recordSale` (passed down as `onRecordSale`), a thin `shipFefo` wrapper that pins the type to `売上出庫` and adds 実売単価/得意先; the preview is the shared `planFefoShipment`, same as `ShipFefoModal`. `ShipFefoModal` and `App.tsx`'s `StockIoModal` show the same 販売単価/得意先 fields when the chosen 出庫区分 is `売上出庫`, so a sale entered from 在庫一覧 lands in this tab too. See `docs/sales-feature.md`.
- `SalesDocumentView.tsx` — 納品書・請求書 tab (right of 売上管理), the sales-side twin of 発注書 + 発注履歴. It lists issued documents (filter / CSV / 再表示 / 取消) and opens `SalesDocumentModal.tsx` (create) — both render the same `SalesDocumentPaper.tsx`, and the modal's preview is built by `draftSalesDocument` from the same `buildSalesDocumentItems` that `issueSalesDocument` saves, so preview and issued document (number, amounts) can't diverge. Candidate lines come from `salesDocumentLines(sales, customerId, from, to, issued)`, which groups the `SalesRow[]` App.tsx already builds by 納品日 + product + unitPrice + taxRate (sales without a customer are excluded). Issued documents are snapshots in their own table (`SalesDocumentItem`, one row per line with the header repeated, `txnIds` = the 売上出庫 rows it covers — own migration `0014_sales_documents.sql`, mirrored in `worker/index.ts`, `txn_ids` stored as JSON text); a sale already on a document of the same kind can't be put on another (`issuedSalesDocumentNos`; `issueSalesDocument` re-checks against current state before saving), but 納品書 and 請求書 are counted separately. **Tax on a document is rounded once per rate over the summed amount** (`salesDocumentTotals`, the 適格請求書 rule) — unlike `salesRows`, which rounds per ledger row, so the two can differ by a few yen on purpose. Issuing/canceling writes **nothing** to the ledger. Issuer info (incl. 登録番号 `T`+13 digits) is per-device `localStorage`, like the 発注書 sender. `resetToSample` clears the documents along with the ledger. Tested in `src/test/salesDocument.test.ts` / `src/test/SalesDocumentView.test.tsx`. See `docs/sales-document-feature.md`.
- `ReceivableView.tsx` — 入金管理 tab (right of 納品書・請求書): 請求書別 / 得意先別 / 入金履歴, plus `PaymentModal.tsx` (入金登録). `PaymentItem` (own table `payment_items`, migration `0016_payments.sql`) is one row per (入金 × 充てた請求書), grouped by `receiptId`; `documentId: ''` is 未消込 (前受・過入金). Invoice status (`未入金`/`一部入金`/`入金済`), 残高, 期限超過 and 売掛金残高 are **never stored** — `receivableRows(salesDocumentItems, payments)` / `customerReceivables` recompute them (請求額 = `salesDocumentTotals().amountWithTax`; 未請求売上 = `SalesRow.amountWithTax` of customer sales not on any 請求書, so it can differ by a few yen from the later invoice). Allocation is the pure `planPayment` (selected invoices in 期限 order, capped at each remaining, fee assigned first-come, leftover → 未消込), shared by the modal preview and `recordPayment`, which re-plans against current state so a stale modal can't over-apply. `deleteSalesDocument` now returns `boolean` and refuses an invoice with payments; `deleteCustomer` refuses a customer with any payment. Nothing is written to the ledger; `resetToSample` clears payments. `DashboardView` shows 期限超過の売掛金 / 未回収アラート from the same `receivableRows` (optional `salesDocumentItems`/`payments` props). Tested in `src/test/receivable.test.ts` / `src/test/ReceivableView.test.tsx`. See `docs/receivable-feature.md`.
- 締め請求 (`ClosingModal.tsx`, opened by the 締め請求 button in `SalesDocumentView` when `onIssueMany` is passed): `Customer.closingDay` (5/10/15/20/25, `31` = 末日, `0` = 都度請求) / `paymentMonths` / `paymentDay` are optional and default to 末日締め・翌月末払い (`customerClosingDay` etc.; the defaults are filled in when `useInventory` loads the state and in `normalizeCustomerInput`). There is **no closing table** — the period is derived from dates (`billingPeriod` = previous month's closing day + 1 → closing day) and issued invoices are ordinary 請求書 in `salesDocumentItems`. `closingCandidates` puts **all** unbilled sales up to the closing date on the invoice (earlier ones are marked 前回以前 by `deliveryDate < periodFrom`, no extra field). 繰越型: `SalesDocumentItem.balanceForward` snapshots 前回御請求額/御入金額/繰越額 (`balanceForward()`: 繰越 = Σ prior invoice remaining − unapplied payments, 入金 = payments since the previous invoice's issueDate, 前回 = 繰越 + 入金 back-calculated); **the invoice's receivable amount stays this period's `amountWithTax` only** (`invoiceGrandTotal` = carry + this period is display-only), otherwise 入金管理 would double count. Bulk issue goes through the pure `prepareSalesDocuments` (re-checks double billing and recomputes the carry against current state, sequential numbers) — `issueSalesDocuments` saves in one PUT and `issueSalesDocument` is its single-item wrapper; the preview uses `draftSalesDocuments`. `SalesDocumentModal` also takes period/due defaults from the customer's terms and attaches the carry for 請求書. Issuer info load/save lives in `salesDocumentIssuer.ts` (shared). Tested in `src/test/billingClosing.test.ts`. See `docs/billing-closing-feature.md`.
- `CustomerMasterView.tsx` / `CustomerModal.tsx` — 得意先マスタ, the last section of the 商品マスタ tab. Mirrors `SupplierMasterView`/`SupplierModal` (modal editing, keyword / show-inactive filter); the per-customer sales usage is the pure `customerRows`/`customerUsage`, which take the `SalesRow[]` App.tsx already builds (so the fallback rules for unrecorded prices live in one place). Tested in `src/test/customer.test.ts`.
- `CostHistoryView.tsx` — 原価履歴 tab. Read-only, mirrors `LedgerView`'s structure (keyword/supplier/date filter over a flat table, no drill-down). Shows every 入荷 with a recorded `unitPrice`, plus a per-row 前回比 (delta vs. the previous record for the same product+supplier). Filtering/aggregation/CSV are pure functions in `useInventory.ts` (`costHistoryRows`, `filterCostHistory`, `costHistoryTotals`, `costHistoryCsv`) tested in `src/test/costHistory.test.ts`. See `docs/cost-history-feature.md`.
- `StockAnalysisView.tsx` — 在庫分析 tab (last tab). Derives ABC ranking / turnover / stagnant stock from the ledger's outbound rows (`売上出庫`+`資材使用`+`調整出庫`+`廃棄`; 移動 is excluded) crossed with current lots, the same "derive from the ledger" pattern as 原価履歴 and 廃棄ロス — no migration, no new table. It owns only the 集計期間 (30/90/180/365日), the 滞留 threshold (30/60/90日), the 安全在庫日数 (3/7/14日), its filter and the selected rows; everything else is pure functions in `useInventory.ts` (`stockAnalysisRows`, `stagnantRows`/`isStagnant`, `stockAnalysisTotals`, `filterStockAnalysis`, `minQuantitySuggestions`, `planMinQuantities`, `stockAnalysisCsv`) tested in `src/test/stockAnalysis.test.ts`. Two rules are easy to break: **`lastOutboundAt`/`stagnantDays` deliberately ignore the period** (a product last shipped 200 days ago must stay distinguishable from one that never shipped), and **`minQuantitySuggestions` skips products with no outbound in the period** (deriving a 発注点 from a pace of 0 would lower it and starve slow movers). Its one mutation is 発注点の見直し提案 → `applyMinQuantities` (passed down as `onApplyMinQuantities`), which updates `Product.minQuantity` in one state update / one PUT and writes nothing to the ledger; the preview is the pure `planMinQuantities`, shared by the confirm dialog and the mutator, same as `planReorder`/`planDisposal`. Outbound value is `出庫数 × Product.costPrice` (the ledger has no unit price on outbound rows) and turnover divides by *current* stock — both documented approximations. See `docs/stock-analysis-feature.md`.
- `LotTraceView.tsx` — ロット追跡 tab. Read-only recall-support view: pick a lot (商品 + ロットNo) and see its 入荷→移動→出庫 as a chronological card timeline plus what is left / what already went out. It owns only the search keyword; the selected `LotTraceKey` lives in `App.tsx` because the 在庫一覧 lot rows' 追跡 button sets it while switching tabs. All the logic is pure functions in `useInventory.ts` (`traceLot`, `chronologicalLedger`, `lotTraceCandidates`, `lotStockRows`, `lotTraceCsv`) tested in `src/test/lotTrace.test.ts`. Lot numbers are generated from the expiry date, so they repeat across products — never key a trace on `lotNo` alone. `chronologicalLedger` is the one place that knows the ledger's ordering quirk (newest-first overall, but a batch recorded in one `addTransactions` call shares a date and is stored oldest-first). See `docs/lot-trace-feature.md`.
- `LedgerView.tsx` — read-only table rendering the transaction ledger, resolving warehouse ids to names/colors via the `warehouses` list. It owns the ledger filter state (keyword / date range / type / warehouse) locally; the filtering, totals and CSV serialization themselves are pure functions in `useInventory.ts` (`filterLedger`, `ledgerTotals`, `ledgerCsv`, `exportLedgerCsv`) so they can be tested without rendering (`src/test/ledger.test.ts`).
- `ProductMasterView.tsx` / `CategoryMasterView.tsx` — inline-edit master tables, both rendered in the 商品マスタ tab (products first, categories below).
- `SupplierMasterView.tsx` / `SupplierModal.tsx` — 仕入先マスタ, the last section of the 商品マスタ tab. Unlike the other masters it edits through a modal rather than inline (9 fields), and owns its keyword / show-inactive filter; the listing + per-supplier inbound-plan usage is the pure `supplierRows`/`supplierUsage` in `useInventory.ts`, tested in `src/test/supplier.test.ts`. Its row action `PurchaseOrderModal.tsx` (発注書, always enabled — not just for suppliers with pending orders) both previews/prints a purchase order built from that supplier's pending 入荷予定 and lets you add new line items directly in the same modal, which calls `onAddPlan` (`addInboundPlan`) to create them as real 入荷予定 (empty `lotNo`/`expiryDate`, same as 発注提案) — since `rows` is rebuilt by `SupplierMasterView` from `inboundPlans` on every render, a newly-added line shows up in the preview immediately. The pure `purchaseOrderRows` in `useInventory.ts` (tested alongside the other inbound-plan pure functions in `src/test/inboundPlan.test.ts`) picks **every** not-yet-received line item for that supplier regardless of whether it was already printed before, so `PurchaseOrderModal` gives each row a checkbox (default: all checked, tracked as an "excluded ids" set so new/added rows default to checked) — `purchaseOrderTotals` and the print button's disabled state are computed from only the checked rows, and an unchecked row's `<tr>` gets `.no-print` so it's skipped by `window.print()` entirely (its checkbox column is `.no-print` unconditionally, so the header/body/footer column count stays consistent between screen and print). Clicking 印刷 calls `onPrint` (`printPurchaseOrder`) with the currently-checked rows plus the supplier/order-date/sender info, which does two things in one call: (1) stamps `InboundPlan.printedAt` on those plans (own migration `0008_inbound_plan_printed.sql` / `inbound_plans.printed_at`, mirrored in `worker/index.ts`'s local `InboundPlan`/`InboundPlanRow` types and its `readState`/`replaceInboundPlans`) — a plan with `printedAt` set is permanently excluded from `selectedRows`/`allSelected`/"すべて選択" and its checkbox is rendered `disabled` (can't be re-selected for a future order, i.e. no unlock action), so double-ordering the same pending plan is prevented; (2) appends a snapshot of what was printed to `purchaseOrderPrints` (own migration `0009_purchase_order_prints.sql` / `purchase_order_prints`, one row per printed line item sharing a `printGroupId`, mirrored in `worker/index.ts` the same way) so it can be re-viewed later — see `PurchaseOrderHistoryView.tsx` below. "Printed" is simplified to "the 印刷 button was clicked" (there's no way to detect whether the OS print dialog was actually completed vs. cancelled). Printing uses the browser's own print dialog (`.po-print-area` / `@media print` rule in `App.css`, no PDF library — the "keep it as a PDF" need is instead met by being able to re-render and re-print the exact same document later). The sender ("発注元") details are a print-form convenience only, persisted to `localStorage` rather than the DB since they aren't inventory data. See `docs/supplier-feature.md`.
- `PurchaseOrderHistoryView.tsx` — 発注履歴 tab. Read-only log of every 発注書 print (one row per print operation, i.e. per distinct `printGroupId` in `purchaseOrderPrints`), filterable by keyword/supplier/date and grouped/aggregated by the pure `purchaseOrderPrintGroups` in `useInventory.ts` (tested in `src/test/purchaseOrderHistory.test.ts`; `printPurchaseOrder` itself is tested in `src/test/inboundPlan.test.ts`). Its row action opens `PurchaseOrderReprintModal.tsx`, a read-only replay of the exact snapshot recorded at print time (no checkboxes, no 明細を追加 — the history is a fixed record) that reuses the same `.po-overlay`/`.po-print-area` print CSS as `PurchaseOrderModal`; printing from there doesn't touch `purchaseOrderPrints` or `InboundPlan.printedAt` again (it's a reprint of an already-recorded order, not a new one). See `docs/purchase-order-history-feature.md`.
- `StocktakeView.tsx` — 棚卸 tab. One row per lot with the book quantity and an 実数 input; counts live in local state keyed by `lotId` (absent key = uncounted) and are only written back when 棚卸を確定 calls `applyStocktake`. Like `LedgerView`, all the logic is pure functions in `useInventory.ts` (`stocktakeRows`, `stocktakeDiffs`, `stocktakeTotals`, `stocktakeCsv`, `exportStocktakeCsv`) tested in `src/test/stocktake.test.ts`. `applyStocktake` deliberately ignores the view's filter and applies every entry in `counts`, so changing the filter mid-count never drops input.
- `DashboardView.tsx` — ダッシュボード tab (first tab; 在庫一覧 is still the default). Summary of stock value, 要発注 (`totalQuantity <= minQuantity`), expiry alerts, 廃棄ロス, and per-warehouse / per-category breakdowns. Its local state is the expiry threshold (7/14/30 days), the 廃棄ロス period, and the set of lots selected for disposal; every aggregation is a pure function in `useInventory.ts` (`dashboardTotals`, `lowStockRows`, `expiringLotRows`, `warehouseSummaries`, `categorySummaries`, `reorderCsv`, `exportReorderCsv`) tested in `src/test/dashboard.test.ts`. App.tsx hides the shared alert banners and stats row on this tab to avoid duplicating them. See `docs/dashboard-feature.md`.
- 発注提案 is the dashboard's other action, and the only one that does **not** touch stock: the 要発注 rows get checkboxes, an editable 発注数/仕入先 per row, and `addInboundPlans(inputs)` (passed down as `onCreateOrders`) creates the 入荷予定 in one state update / one PUT. `reorderSuggestions(products, inboundPlans, suppliers, warehouses, options?)` builds on `lowStockRows`, subtracting each product's `remainingInbound` so an already-ordered product suggests 0 (no double ordering), and inherits supplier / warehouse / unitPrice from that product's most recently created plan (an inactive or deleted supplier is not inherited). The preview is the pure `planReorder(rows, productIds, suppliers, overrides?, from?)`, shared by the confirm dialog and the mutator, same as `planDisposal`. Created plans carry an **empty `lotNo`/`expiryDate`** (unknown at order time) — which is why `InboundPlanModal` accepts an empty lot number and `ReceiveInboundModal` fills one in from the expiry. Nothing is written to the ledger: stock only moves at `receiveInboundPlan`. See `docs/reorder-feature.md`.
- 一括廃棄 is the one mutation reachable from the dashboard: the expiry-alert rows get checkboxes and `disposeLots(lotIds)` (passed down as `onDispose`) disposes them in full, writing one `廃棄` row per lot. It **removes** the emptied lots rather than leaving them at quantity 0, because App.tsx's 期限切れ banner counts zero-quantity lots and would never clear otherwise. The preview is the pure `planDisposal(products, lotIds)`, shared by the confirm dialog and the mutator. Disposal history is aggregated back out of the ledger by `disposalTransactions` / `disposalRows` / `disposalTotals` / `disposalCsv` (`src/test/disposal.test.ts`) — the loss amount uses the disposed lot's `lotUnitCost` (`disposeLots` writes it onto the `廃棄` row as `unitPrice` since the lot itself is gone by the time `disposalRows` runs); older records or lots that never had a cost set fall back to the product's *current* `costPrice`, an approximation.
- バーコード読み取り (`docs/barcode-feature.md`): `ScanInput.tsx` is the one scan field used by 在庫一覧 (`App.tsx`), 棚卸 (スキャン数え), `SalesEntryModal`, `ShipFefoModal` and `InboundPlanView`; each call site passes a `hint` saying what a scan does on that screen (shown as a small「スキャンすると：…」line that the scan result replaces) — give a new call site one too. A USB/Bluetooth scanner is a keyboard (digits + Enter), so the field just handles Enter (and `preventDefault`s it so it never submits a surrounding form) — tests simulate a scan with `user.type(field, '4901234567894{Enter}')`. Camera reading is `CameraScanner.tsx` with ZXing (`@zxing/browser`/`@zxing/library`, pinned versions; not the native `BarcodeDetector`, which is missing on desktop Chrome/iOS); it is `React.lazy`-loaded by `ScanInput` and dynamically imports ZXing, so **never import `CameraScanner` or `@zxing/*` statically** (same main-bundle reason as xlsx). Lookup is the pure `findProductByScan` (JAN exact, then SKU exact). A JAN identifies a product, never a lot: 棚卸 asks which lot to count when a product has several (remembered per product, scoped by the category/warehouse filter but not the keyword). `janCodeError` now checks the check digit too (`isValidJanCode` wraps it) — sample/fixture JANs must have valid check digits. `eanModules` draws EAN-13/8 for `BarcodeSvg`; `src/test/barcode.test.ts` verifies it by decoding the bars with ZXing's own reader.
- `badges.tsx` — the shared `ExpiryBadge` / `WarehouseDot` presentational components used by both the inventory table and the stocktake table. `ExpiryBadge` switches to a plain date past 7 days, so `DashboardView` uses its own `DaysLeftBadge` for the wider 14/30-day ranges.
- `NumberInput.tsx` — the shared `<input type="number">` wrapper used by every numeric form field (数量 / 最低在庫数 / 価格 …). It keeps the typed text in local state so clearing the field leaves it empty and reports `0` (or `emptyValue`) to the parent. **Don't write `value={someNumber} onChange={e => set(+e.target.value)}` directly** — `+'' === 0` is re-rendered into the field, so backspace looks broken on the last digit. (`StocktakeView`'s 実数 column is exempt: its counts are string-keyed and an empty value means 未カウント.)
- `ConfirmDialog.tsx` / `useConfirm.tsx` — in-app replacements for `window.confirm` / `window.alert`. Use `const { confirm, confirmDialog } = useConfirm()` (or `useNotify`) and render the returned node; **don't call the native `confirm`/`alert`** — they are silently suppressed in embedded browsers and in tabs where the user checked "don't show more dialogs", which makes the button look dead. The two files are split because a file exporting both a component and hooks breaks React Fast Refresh (oxlint `react(only-export-components)`).
- Excel import/export and CSV export (`exportCsv`, `exportExcel`, `importExcel` in `useInventory.ts`) use the `xlsx` package (SheetJS). It is installed from SheetJS's own CDN tarball (`https://cdn.sheetjs.com/xlsx-<ver>/xlsx-<ver>.tgz` in `package.json`), **not** the npm registry: npm's `xlsx` stopped at 0.18.5, which has unfixed prototype-pollution / ReDoS advisories on the read path. Because of that, `npm outdated` / Dependabot won't report new SheetJS versions — check https://cdn.sheetjs.com/ and bump the URL by hand. `xlsx` is **lazy-loaded** (`loadXlsx()` → `import('xlsx')`, a separate ~490 kB chunk) so the main bundle stays under Vite's 500 kB warning — never add a static `import ... from 'xlsx'`. For the same reason `App.tsx` loads the tab views that aren't needed at startup (`SalesDocumentView`, `ReceivableView`, `LotTraceView`, `CostHistoryView`, `StockAnalysisView`, `PurchaseOrderHistoryView`) with `React.lazy` inside one `<Suspense>`; the pure functions stay in `useInventory.ts` (main bundle), so only the UI is split; `exportExcel`/`importExcel` are therefore async, and `App.tsx` reports a failed load through `notify`. Import matches rows by `SKU` + `ロットNo`(lot number) and only touches matching lots' quantities, diffing against current quantity to decide 入庫 vs 出庫 and by how much.
- There are nineteen different CSV exports (在庫一覧 / 入出庫帳票 / 棚卸表 / 要発注リスト / 入荷予定 / 受注一覧 / 廃棄ロス / ロット追跡 / 仕入先一覧 / 原価履歴 / 発注履歴 / 在庫分析 / 売上明細 / 売上集計 / 得意先一覧 / 納品書・請求書 / 請求残高 / 売掛金残高 / 入金履歴). Their button labels, tooltips and download filenames all come from `CSV_EXPORTS` + `csvFileName` / `csvExportLabel` / `csvExportHint` in `useInventory.ts` so they stay distinguishable — add a new key there rather than hard-coding a filename or a bare 「CSVエクスポート」 label at the call site.
